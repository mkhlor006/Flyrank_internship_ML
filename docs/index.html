Content Refresh Prioritisation Using Machine Learning

A research project from the FlyRank ML Internship

Lorreta Makhuvele

Abstract

This study investigates whether machine learning can help FlyRank content teams prioritise which pages should receive human refresh review when reviewing a large content portfolio. The analysis uses the FlyRank internship dataset and combines historical search visibility, engagement and content characteristics to compare a learned Logistic Regression model with a rule-based baseline. Under the original client-holdout evaluation, the Logistic Regression model achieved a measured Precision@50 of 0.76 compared with 0.44 for the rule-based baseline. A separate validation audit showed that measured performance was sensitive to validation design, with Precision@50 of 0.90 under a row-level split and 0.40 under a client-grouped split. The result is a decision-support workflow for prioritising human review, not evidence that refreshing a page will itself cause better traffic, clicks or conversions.

1. Introduction / Problem Statement

In a content operation such as FlyRank's, a team may have many pages that could potentially be reviewed for improvement, but review time is limited. The operational question is therefore not simply which pages have changed, but which pages should be placed near the front of the human review queue.

This project treats content refresh prioritisation as a ranking problem: use observable search-performance, engagement and content signals to order pages for potential review. The workflow is designed for a realistic decision-support setting in which a reviewer can inspect the evidence behind a recommendation before deciding whether any content change is appropriate.

The case study therefore focuses on prioritisation rather than guaranteed recovery. A model score identifies pages that may deserve attention first; it does not establish that a refresh will cause improved performance, and the final action remains with the human reviewer.

2. Data

The analysis uses two related parts of the FlyRank internship data workflow. Warehouse development and signal auditing used the fixed Hugging Face release FlyRank/internship-warehouse, build flyrank_pseudonymized_warehouse_release_v20260703. The warehouse contains pseudonymised search and content-performance data and is the reference release for the internship.

For the warehouse-based development and audit work, the main table used was fact_content_daily_performance. The development slice used was March 2026 rather than the final month. The warehouse daily facts run from 27 January 2025 through 30 June 2026. The final sealed month was not used as the development slice.

The supervised modelling experiments used the anonymised starter playground included in the repository: data/raw/content_refresh_anonymized.csv. After the preparation pipeline and eligibility rules, this produced the 30,000-observation modelling dataset used for the model comparison and validation experiments.

2.1 Observation Grain

The prepared modelling dataset contains one row per pseudonymised content item for the modelling population. The warehouse daily performance table has a daily client-by-content grain, so the warehouse analysis was kept separate from the prepared 30,000-row modelling dataset rather than flattening the full daily warehouse without an explicit window.

2.2 Fields and Exclusions

Predictive inputs were based on observable search, traffic, engagement and content characteristics available before the modelling decision. Numeric features included historical impressions, clicks, sessions, AI sessions, content age, days since update, CTR, average position, engagement and scroll measures, together with search-volume and competition fields. Categorical features included content type, search intent, competition, freshness, content-length, impression and position tiers.

The target is_declining_label, together with trend_direction and trend_pct, was excluded from the predictive inputs because these fields are directly related to the decline definition. content_id and client_id were retained for tracing and grouped validation but were not used as model predictors. Provider/model metadata such as provider_used and model_used was also excluded from the predictive feature set.

No client names, domains, raw URLs, private queries, credentials or raw exports were included in the public paper. The warehouse release itself is pseudonymised and public-safe for the internship workflow.

3. Methodology

3.1 Feature Construction

The modelling feature vector was generated with the repository's feature-preparation pipeline. The final prepared dataset contained 30,000 observations and 52 columns, including identifiers, predictive features, engineered fields and the target label.

Predictive inputs combined numeric and categorical content/search features. Highly skewed traffic variables were represented with log-transformed versions, while categorical fields were handled as categorical variables in the modelling pipeline.

3.2 Label Definition

The target was is_declining_label, defined in the starter preparation workflow as trend_direction == "down". This is a proxy label for the current-window decline condition, not a future-looking outcome. It should therefore be interpreted as a supervised ranking target for the internship workflow rather than proof that a page will decline in the future or that a refresh will reverse a decline.

3.3 Rule-Based Baseline

A transparent rule-based refresh score was established before comparing learned models. It combines visibility, freshness risk, position-opportunity and content-depth signals and produces an ordered review queue with reason codes.

3.4 Learned Models

Logistic Regression, Decision Tree and Random Forest models were compared. The selected Logistic Regression pipeline used standardisation for numeric inputs and balanced class weights, with a maximum of 1,000 iterations. Model selection focused on Precision@50 because the operational decision is about how useful the top-ranked review queue is.

3.5 Validation Design

The original model comparison used a client-holdout split: whole clients were assigned to either training or testing, with no client overlap between the two sets. The training set contained 26,581 observations and the test set contained 3,419 observations, with 26 training clients and 6 held-out test clients.

A separate validation audit compared a row-level split with a client-grouped split. The purpose was to test how sensitive measured performance was to the validation design and to provide a more cautious assessment of generalisation to unseen clients.

3.6 Leakage Checks

The feature vector was checked for target-derived fields, future-looking columns and identifier leakage. The final predictive matrix excluded the target, trend-derived fields, client/content identifiers and provider/model metadata. No forbidden future-looking features were included in the final modelling matrix.

5. Limitations and Honest Framing

The model should not be interpreted as a causal system. A high model score does not demonstrate that refreshing the associated page will increase traffic, clicks or conversions.

The observed performance also depends on the dataset, label definition, selected features and validation split. Results measured on these experiments should therefore not be treated as universal performance estimates.

Content age should also be interpreted in context rather than used as an automatic reason to refresh a page.

6. Ranked Recommendations

  1. Use the model as a prioritisation aid for human review rather than an automatic refresh trigger.
  2. Combine model scores with concrete page-level evidence such as search visibility, position, traffic and content characteristics.
  3. Require a human reviewer to confirm the recommended action before changing content.
  4. Monitor model performance using client-grouped validation when assessing generalisation to unseen clients.
  5. Retrain or re-evaluate the system when the data distribution, content strategy or operational use case changes materially.
